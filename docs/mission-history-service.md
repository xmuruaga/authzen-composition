# Mission History Service: reference History Authority (non-normative)

This document describes the Mission History Service (MHS) in this repository: one way to meet the History Authority requirements of the AuthZEN Mission Composition Profile (its History Authority section and ordering rules). Nothing here is normative. A deployment may use its PDP's evidence store, the Mission's issuer, or any other service that meets the profile's requirements.

## What the reference does, and what it does not

| Profile requirement | Reference (`authzen_composition/mhs.py`, `http_binding.py`) | Production deployment |
|---|---|---|
| Writer authenticated from a verified credential | `MHSHttpApp` takes a deployment-supplied `Authenticator`; there is no default. `StaticTokenAuthenticator` (opaque secret to identity) is a test stand-in. `MissionHistoryService(trusted_writers=...)` restricts writers to one set for every Mission; left empty, any authenticated identity writes, PDPs and auditors included | Verify a workload credential: an mTLS client certificate or a signed workload token, for example as the IETF Workload Identity in Multi System Environments (WIMSE) working group describes |
| Gapless next-position admission; idempotent `admission_id` | Implemented under a process lock | Must be linearizable at the authority, for example a conditional write on the Mission's next position |
| Acknowledge an admission or an outcome only once durable | **Not demonstrated.** The reference is in memory; `admit` returns after an in-memory append. Tests simulate a lost acknowledgement, not a lost write | Commit the record (fsync, quorum write or transactional commit) before replying |
| Outcome once, only by the admitting writer; repeats idempotent; no classes on `failed`; no class empty or containing `*`; an Act's action and resource non-empty strings | Implemented and tested | Same |
| Authenticated reads in Admission Order | Implemented; the PDP also checks positions are exactly 1 to n, and its HTTP client refuses a history with a record that is not a valid Act Record (a member missing, of another type or outside its values). Over HTTP only the PDPs (`pdps=`) and the auditors (`auditors=`) read, each set the same for every Mission (a per-Mission designation is the deployment's); a writer cannot. Error answers name neither the next position nor the writer that admitted an Act, though a writer can still learn how many Acts a Mission holds by probing positions, since positions are what it writes | Same; replicas may serve reads of durable records only (stale reads fail at admission, while a record that could still be lost would make a view that is not a prefix of the history). Apply the access control and retention of the audit records of the resources involved (profile, Privacy considerations), and never give the agent a credential the History Authority accepts |
| One set of Restricted Sequences per Mission | `history(mission, policy=digest)` pins the first digest and refuses another (`PolicyMismatch`). `MissionHistoryService(new_mission_policies=...)` or `designate(...)` restricts which digests a new Mission may be pinned to; a pin already set never moves. Over HTTP only the identities configured as PDPs (`MHSHttpApp(..., pdps=...)`) may name a digest | The pin must be stored with the Mission, linearizably, like the next position. Designate the new set when a rollout should move new Missions to it. Only PDP credentials may pin |
| Bounded input and Mission length | An identifier (Mission, action, resource, `admission_id`) of at most 1024 characters; at most 16 result classes per Act, each of at most 128 characters; with `MissionHistoryService(max_acts=...)`, at most that many Acts per Mission. Anything beyond is refused (`400 Bad Request`), and a PEP then denies without acting | Choose bounds so that the longest Mission's history stays within what a PDP reads (the reference client reads at most 16 MiB) |
| Never forget a Mission while it can be decided; a tombstone after; refuse reads and admissions after a loss (item 8) | **Not implemented.** The reference holds histories in memory and deletes nothing | Retain every record until the Mission has ended and its credentials have expired, keep a tombstone of its identifier, and refuse reads and admissions for the Missions a restore or failover may have affected |
| Stranded Open Acts closed only at the top | `close_stranded(mission, seq, operator)`, for configured operators; records `completed` with no classes. Not exposed over HTTP | Expose it only on an operator interface, for use once the PEP is stopped, its resource credential revoked, and no effect of the Act is queued or scheduled at the resource |

The reference shows the logic of the mechanism. It does not show availability, durability or performance, and it must not be deployed as is.

## Operating notes

* **Cost per decision.** Each evaluation reads and scans the whole Mission history: the PDP keeps no history between decisions, by design. Cost grows linearly with the length of the history, with the number of Restricted Sequences, with the steps of a sequence that has persistent steps, and with the number of result classes per Act times the label domain; a sequence the candidate matches no step of is skipped without scanning. A measurement of this Python reference on a laptop, in the worst case where the candidate matches a step of every sequence, gave one to three seconds per decision for 10,000 Acts under 50 sequences, depending on the machine's load. Plan PDP capacity for the longest Missions, or bound Mission length.
* **Closing a stranded Act ends its sequences.** An operator-closed Act counts at the conservative top for the rest of the Mission. Every later Act that would complete a sequence through that step is denied `prohibited_composition`, or routed to a person if the sequence is requestable. Closing restores progress for other sequences; it does not restore the closed one. When a PEP crashes in the middle of a sequence that the agent still needs, ending the Mission and starting a governed new one is often the realistic recovery.
* **No operator route on the wire.** The binding below has no route to close a stranded Act or to designate the sets new Missions may be pinned to; `close_stranded` and `designate` are in-process calls. A deployment needs an operator-only interface for it, separate from the PEP-facing binding, gated as the table above says. Without one, a Mission that a crashed PEP stalled under rule 5 can only be released out of band.
* **Stored denials.** The reference PDP keeps each requestable denial until its window closes (`request_ttl`, 15 minutes by default) or, once approved, until its approval expires; at most `max_pending_per_mission` (64 by default) per Mission at once, past which a denial is not requestable. The Access Request Service keeps a task, and its `Idempotency-Key`, for 24 hours after the task's `expires_at`.
* **Approvals under contention.** The reference PDP spends an approval on the permit it produces, before the PEP admits (profile, Approvals), and honors it only for the PEP that requested it when it knows the caller (over HTTP). An approval is valid for `approval_ttl` after the person decides (5 minutes by default), whatever is left of the access request's window. If another Act takes the approved position first, the admission conflicts, the PEP evaluates again at a new position, and the person has to approve again. In a busy Mission, route approvals for Acts whose sequences other PEPs are also advancing with this in mind.

## HTTP binding

Every request carries a workload credential. The service derives the writer or reader identity from it and never reads an identity from the body. It authenticates before it routes or reads the body: a request without a valid credential gets `401 Unauthorized`, with a `WWW-Authenticate: Bearer` challenge, whatever its method, path or body, so an unauthenticated caller learns nothing about the service, not even which routes exist or whether its request was well formed. An authenticated caller that may not do what it asks gets `403 Forbidden` (RFC 9110), so a PEP can tell a failed credential, which it retries, from a refusal, which is final. A body up to the size limit is still consumed after the answer is decided: a server that answers with the body unread can reset the connection, and the PEP then sees an outage instead of the `401`.

`{id}` is the Mission id percent-encoded as one path segment, every character outside the RFC 3986 unreserved set encoded, so a URI id keeps its `/` as `%2F`. The service splits the path before it decodes it. A WSGI server decodes `PATH_INFO` first, so the reference reads the raw request target when the server provides it (`RAW_URI` or `REQUEST_URI`); behind a server that does not, an id containing `/` cannot be addressed. A raw request target that is not ASCII is refused with `400 Bad Request`: RFC 3986 percent-encodes every other octet, and read raw, the same id would name two Missions.

* `POST {mhs}/missions/{id}/acts` with `{"seq": n, "action": {"name": "..."}, "resource": {"id": "..."}, "admission_id": "..."}`
  * `201 Created` with the Act Record if `n` is the next position, or if this writer already used `admission_id` for the same position, action and resource (the existing Act is returned). A `201` whose Act already has an outcome other than `open` is not an acknowledgement (profile, rule 3): the PEP does not act.
  * `admission_id` is optional here; a conforming PEP always sends it (profile, PEP processing rules), and an Act admitted without one takes any report from its writer.
  * `409 Conflict` with `"reason": "seq_conflict"` if `n` is not the next position, or if this writer already used `admission_id` for a different Act. The PEP evaluates again.
  * `401 Unauthorized` if the credential does not verify; `403 Forbidden` if the writer is not one the service trusts; `400 Bad Request` for an identifier beyond the bounds above, or an admission into a Mission that holds `max_acts` Acts.
* `PATCH {mhs}/missions/{id}/acts/{n}` with `{"outcome": "completed", "result_classes": [...], "admission_id": "..."}` or `{"outcome": "failed", "admission_id": "..."}`; `result_classes` may be left out, which records none (the conservative top)
  * `200 OK` the first time, and on an identical repeat.
  * `409 Conflict` with `"reason": "outcome_conflict"` for a different outcome on an Act that already has one, for a position that holds no Act, or for an Act admitted with an `admission_id` when the report names another or none.
  * `403 Forbidden` if the caller is not the writer that admitted the Act.
  * `400 Bad Request` for `failed` with result classes, for a result class that is empty or contains `*`, for more or longer result classes than the bounds above, or for any `outcome` other than `completed` or `failed`.
* `GET {mhs}/missions/{id}/acts` or `GET {mhs}/missions/{id}/acts?policy={digest}`
  * `200 OK` with `{"acts": [...], "next_seq": n}` for a PDP or an auditor.
  * `403 Forbidden` for any other authenticated caller, a writer included, whatever its query: a history holds every Act's action, resource and classes, which can be personal data. For a PDP or an auditor, a malformed query (`policy` given twice or empty, or more than 8 fields) is a `400 Bad Request`.
  * A PDP names the policy digest of the Restricted Sequences it applies. The first read that names one pins it for the Mission; a read naming another gets `409 Conflict` with `{"error": "...", "reason": "policy_mismatch"}`. Only a caller authenticated as a PDP may name `policy`; any other caller that names it gets `403 Forbidden`, so a PEP cannot pin a Mission to a set of its choosing. A read without `policy` (an auditor's) does not pin. A first read naming a digest the deployment has not designated for new Missions (`designate`) also gets `409 Conflict` with `"reason": "policy_mismatch"`, and pins nothing.

Input is validated strictly, and anything malformed is answered `400 Bad Request` with `{"error": "..."}`, never a server error:

* the body is a JSON object of at most 64 KiB, with at most 64 levels of objects and arrays (the body included), framed by a `Content-Length` it matches and by no `Transfer-Encoding`, since a proxy and the service could disagree on where a body framed both ways ends; duplicate members, `NaN` and `Infinity` are rejected, because two parsers that resolve them differently would read different requests from the same bytes;
* `seq` is a positive JSON integer (not `true`, a float or a string), and `{n}` in the path is a positive decimal integer without signs, leading zeros or non-ASCII digits;
* `action.name`, `resource.id`, `admission_id`, `outcome` and each entry of `result_classes` are non-empty strings, and `result_classes` is an array.

Every error response, whatever its status, has the body `{"error": "..."}`; a `409 Conflict` also carries `reason` (`seq_conflict`, `outcome_conflict` or `policy_mismatch`), so a client can tell them apart without parsing `error`. Any other path is `404 Not Found`, and any other method on these paths is `405 Method Not Allowed`.

`authzen_composition/remote.py` is a client for this binding (`RemoteHistoryAuthority`), and `authzen_composition/pdp_http.py` exposes the reference PDP over the Access Evaluation API, so PEP, PDP and History Authority can run as separate processes; `e2e/` runs them that way. The clients fail closed on an answer larger than 16 MiB or not read in full within their timeout, so a faulty or hostile peer cannot hold or exhaust a PDP or a PEP, and a PEP takes the Access Request Endpoint from PDP metadata only over HTTPS (plain HTTP only to the same machine), without user information, and, when the deployment lists trusted origins, on one of them. Its metadata advertises the Obligations Core and `mission_record`. With an `AccessRequestService` (`authzen_composition/arap.py`) it also plays ARAP's Access Request Service in the shared-state form: `POST /access/v1/requests` takes a submission bound by `denial.evaluation_id`, `GET /access/v1/requests/{task}` returns `{"task": ..., "result": ...}`, the Task Handle and, once decided, the result, and a person decides at `POST /approvals/v1/tasks/{task}` with `{"decision": "approve"}` or `"deny"` (the deployment's approval interface, not ARAP). Errors use ARAP's problem types, except these, which carry `{"error": ...}` like every other route: a failed credential (`401`), a caller the service does not authorize (`403`: not a configured submitter, or an approver who is not eligible), and a body that is not a JSON object or a decision other than `approve` or `deny` (`400`). A task is `pending`, then `approved`, `denied`, `expired` (its window closed undecided) or `failed` (the denial was spent or dropped before the decision); a task still pending when its `expires_at` passes answers `200` with `expired` once and `410` with `task_expired` after that, as a decided task does after its `expires_at`, and a task the service has forgotten is `unknown_task`. Binding artifacts are not implemented, so the reference does not meet ARAP's Interoperability Baseline; see the README.

### PDP binding

`authzen_composition/pdp_http.py` serves:

* `GET /.well-known/authzen-configuration`, without a credential: the metadata, which lists `urn:openid:authzen:capability:obligations` in `capabilities` and `mission_record` in `supported_obligations` (from which a PEP discovers the profile), and, with an Access Request Service, ARAP's capability URN and `access_request_endpoint`;
* `POST /access/v1/evaluation`, with a PEP's bearer credential: one Access Evaluation. The answer is `200 OK` with the decision; `401 Unauthorized` (with `WWW-Authenticate: Bearer`) for a failed credential; `400 Bad Request` with `{"error": ...}` for a malformed request, such as a `context.mission` that is not an object or whose `id` or `issuer` is not a non-empty string. Adoption lists are read leniently: one that is not an array reads as absent, and an entry that is not a non-empty string is ignored;
* the ARAP routes above, when an Access Request Service is configured.

The request bodies have the limits of the History Authority binding above (64 KiB, 64 levels, no duplicate members, `NaN` or `Transfer-Encoding`): a PEP carries in `properties` a digest or a version identifier of what an effect discloses, not the content itself. `CompositionPDP` is the composition layer only: it permits whatever checks (a) to (d) of the profile's order of checks do not deny, and a deployment puts its other policy in front of it or around it. Its defaults: a requestable denial's window is 15 minutes (`request_ttl`), an approval lasts 5 minutes from the decision (`approval_ttl`), and `retry_after` is 60 seconds with `policy_mismatch`. The clients' timeout is 5 seconds, and the reference PEP evaluates again at most 5 times after losing its position, then gives up with its own reason `too_many_conflicts`.

There is no `evaluations` (batch) route and no Search route. A PEP evaluates again after a `history_pending` with a backoff: it cannot read the history, and the denial carries `retry_after` only for `policy_mismatch` after an approval.

A complete exchange: the PEP evaluates; a requestable denial carries `context.reason`, `context.evaluation_id` and `context.access_request.expires_at`; the PEP submits the denied request with `denial: {"evaluation_id": ..., "expires_at": ..., "reason": ...}` and an `Idempotency-Key` header, and gets `202` with `{"task": {"id", "status", "status_endpoint", "expires_at"}}`; once a person approves, the task's `result` is `{"mode": "reevaluate", "approval": {"id", "approved_until", "approved_at"}}`, and the task's `expires_at` moves to no earlier than `approved_until`, so that the result stays retrievable while the approval can be used (a PEP stops polling at the `expires_at` it last saw, so it polls more often as that time nears); the PEP evaluates again with `context.approval` set to that approval and acts on `next_action` if it is denied. The service forgets a task, and its `Idempotency-Key`, 24 hours after the task's `expires_at` (ARAP keeps a key at least that long after a terminal status), checking on every call; a retry with the key before then returns the same task. A submission is compared with the denial structurally, on the Subject, Resource and Action and on `context.mission` and the adoption declarations as the PEP sent them, members the PDP ignores included.

Act Record:

~~~ json
{
  "seq": 1,
  "action": { "name": "read_record" },
  "resource": { "id": "hr:emp-4471" },
  "outcome": "completed",
  "result_classes": ["personal_data.salary"],
  "recorded_by": "https://pep.hr.example"
}
~~~

## PEP behavior in the reference

`authzen_composition/pep.py`:

1. evaluate, listing `obligations` in `supported_mandatory_extensions` and `mission_record` in `supported_obligations`; a permit that carries any other obligation, more than one `mission_record`, or a `mission_record` whose properties are not exactly `mission` (this Mission) and an `expected_seq` from 1 to 2^53 - 1, is a deny (`obligation_not_understood`, the reference PEP's own reason, not a profile denial reason), and nothing is admitted; on a permit with `mission_record`, admit at `expected_seq` with a fresh `admission_id`; for a request that presents an approval, neither admit nor act from its `approved_until` on (`approval_expired`, the reference PEP's own reason), and record `failed` if it was admitted already;
2. if the acknowledgement is lost, retry once with the same `admission_id`; an answer that returns the Act with an outcome already recorded is not an acknowledgement; if there is still no acknowledgement, deny (`mission_record_unavailable`, again the reference PEP's own reason) and do not act, and keep a `failed` outcome for that position to deliver with the others (the admission may have committed; `failed` is true, since the Act never ran); an answer that refuses the admission for good (`400`, `401`, `403`) shows nothing was admitted, so the PEP denies and keeps nothing;
3. on `409`, evaluate again from the start;
4. perform the action only after the acknowledgement;
5. record `completed` with classes; record `failed` only when the action raised `NotPerformed`; any other error leaves the Act open. If the action returns `EffectPending` (a queued or scheduled call), the Act stays open until the integration calls `effect_landed()`, or `effect_cancelled()` once the resource confirms it never will;
6. keep any outcome it could not write and deliver it again with `redeliver()`; an outcome the authority refuses for good, because the Act already holds another outcome or does not exist, the position holds another writer's Act (`403`), or it rejects the outcome itself (`400`), is not retried and is kept in `refused` for the operator; a failed credential (`401`) is retried. Treat every such refusal as an incident (except the `failed` kept for an admission that never committed): an operator closed an Act whose PEP was still running (which the profile forbids, History Authority item 7, and the Acts it held back may have run meanwhile), another holder of the PEP's writer identity reported first, the authority lost an Act it acknowledged, or a classifier produced a class the authority refuses.

The reference `ReferencePEP` takes the decision point it is given. A PEP sends requests that carry a Mission only to a PDP whose metadata lists `mission_record` (profile, PEP processing rules): `RemotePDP.issues_mission_record()` reads it, and the end-to-end tool hosts refuse to start without it.

## Colocation

The MHS may be colocated with the PDP, as ARAP allows for its Access Request Service. Colocation does not change the requirements: writers still authenticate and admission is still serialized.
